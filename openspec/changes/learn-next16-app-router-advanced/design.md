## Context

See [proposal.md](./proposal.md) for motivation. Current state of this codebase (Next.js 16.2.10, App Router, verified against `node_modules/next/dist/docs` and Context7 `/vercel/next.js/v16.2.9`):

- `next.config.ts`: only `reactCompiler: true` and `images.remotePatterns`. `cacheComponents` is **not** enabled.
- Data mutations live in `src/server/actions/{members,likes,messages,admin}.ts`, all `"use server"`, all wrapped in blanket `try/catch` that mostly `console.error`s and returns `undefined` or `{status:"error"}`.
- `getMemberById` is the only place using React's `cache()` for request memoization.
- `src/proxy.ts` (renamed middleware) checks `auth.api.getSession()` and redirects — no per-route `unauthorized()`/`forbidden()` usage.
- No `loading.tsx`, no per-segment `error.tsx` (only a root `error.tsx`), no parallel/intercepting route folders (`@slot`, `(.)folder`), no `use cache`/`cacheLife`/`cacheTag`/`updateTag`, no `revalidateTag`, no `after()`, no `instrumentation.ts`, no test runner in `package.json`.
- Auth: `better-auth`, sessions read via `headers()`/`auth.api.getSession()`.

This design groups the learning roadmap into two tracks and states, for each item, the current gap and the specific doc-backed nuance to internalize. Conceptual theory for each topic lives in [theory.md](./theory.md) (read before practicing); the actual practice tasks — now framed as "ideate several options, then build one" rather than one prescribed exercise — are in [tasks.md](./tasks.md).

## Goals / Non-Goals

**Goals:**

- Enumerate the framework topics worth deep, senior-level understanding, distinguishing "never touched" from "touched but shallow."
- For every "touched but shallow" topic, cite the concrete nuance/gotcha this codebase currently glosses over, so practice has a real target instead of re-reading docs.
- Keep each topic small enough to become its own follow-up exploration/implementation chat.

**Non-Goals:**

- Not a redesign of the dating-app product — practice exercises may be standalone playground features with no product value; feature essence never matters, only the framework concept exercised.
- Not an implementation plan — no code changes here (`tasks.md` lists exercises to be executed as separate, later changes).
- Pages Router, i18n domain routing, and static export remain fully out of scope (no tasks at all) — not applicable to this app's stack.
- Testing (Vitest/Playwright) is explicitly out of scope — already familiar territory, not a learning gap.

### Track B — Nuances of features already used here (the "senior polish" track)

These are the ones the user specifically asked for: things partially used, where the deeper mechanics/gotchas are the differentiator.

| #   | Topic                                                                               | Current shallow usage                                                                                                                                                                                                                   | The nuance/gotcha (doc-backed)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| --- | ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| B1  | **Server Action security model**                                                    | All actions in `members.ts`/`likes.ts`/`messages.ts` do `requireAuthUser()` then blanket `try/catch`. `toggleLikeMember(targetUserId, isLiked)` **trusts the client-supplied `isLiked` boolean** instead of re-deriving it from the DB. | Docs (`02-guides/server-actions.md`) call this out explicitly: "a client legitimately tells the server which item, but should not supply the row's state." Also: actions are POST endpoints reachable by anyone who can send the request — framework CSRF/origin checks, body-size limit, and closure-variable encryption (`NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`) are not a substitute for in-action auth/ownership checks. Client dispatch is **sequential per client** (no `Promise.all` parallel actions) — a real gotcha if UI ever fires multiple actions at once. |
| B2  | **Expected vs. uncaught errors**                                                    | Every action wraps everything in `try/catch`, sometimes swallowing failures silently (e.g. `fetchCurrentUserLikeIds` returns `undefined` on error, `getMemberPhotosById` too).                                                          | Next's model (`01-getting-started/10-error-handling.md`) distinguishes **expected errors** (model as return values + `useActionState`, never throw/catch for these) from **uncaught exceptions** (let them bubble to `error.tsx`). Blanket try/catch-and-log conflates the two and hides real bugs. Also: `redirect()` throws a control-flow exception (`NEXT_REDIRECT`) — wrapping it in `try/catch` silently breaks the redirect, a classic trap this codebase hasn't hit yet only because no action currently calls `redirect()`.                                   |
| B3  | **`revalidatePath` mechanics**                                                      | Used everywhere (`members.ts`, `likes.ts`) as the only invalidation tool, always with literal paths.                                                                                                                                    | `revalidatePath` works via an internal **soft-tag** system (`_N_T_/...` per route segment); a page vs. layout distinction requires the `type` param for dynamic paths; in Server Functions it currently also refreshes **all previously visited pages** on next navigation (a documented, temporary quirk) — worth knowing so it isn't mistaken for a bug.                                                                                                                                                                                                             |
| B4  | **Choosing between `revalidatePath` / `revalidateTag` / `updateTag` / `refresh()`** | Only `revalidatePath` is used.                                                                                                                                                                                                          | Each has a distinct consistency guarantee: `updateTag` = immediate expiry + read-your-own-writes in the same response; `revalidateTag` = stale-while-revalidate (does **not** block the current response); `refresh()` = re-render without invalidating cache, for state that lives outside the cache. Picking the wrong one silently changes whether a user sees their own write immediately.                                                                                                                                                                         |
| B5  | **`fetch()` caching & request memoization**                                         | Not used for external data (Prisma direct), but relevant the moment any external API is called.                                                                                                                                         | `auto no store` vs `force-cache` vs `no-store`; `next.revalidate` "lowest value wins" when the same URL is fetched with different revalidate times in one route; memoization is **per render pass only** and does **not** apply inside Route Handlers; HMR dev cache can mask "fresh data" bugs locally.                                                                                                                                                                                                                                                               |
| B6  | **`cookies()` / async request APIs**                                                | Read via `headers()` in `src/proxy.ts` for session lookup; no direct app-level cookie read/write.                                                                                                                                       | `cookies()` is async (sync access is deprecated-but-tolerated); **read-only in Server Components**, read/write only in Server Functions/Route Handlers; `.set`/`.delete` after streaming starts is impossible by HTTP's nature — this is _why_ the write-only-in-actions rule exists, not an arbitrary framework limitation. Mutating a cookie in a Server Action auto-triggers a re-render in the same response, same as `updateTag`/`redirect`.                                                                                                                      |
| B7  | **Images (`next/image` + Cloudinary)**                                              | `MemberImage.tsx`/`next-cloudinary` used for rendering; `remotePatterns` restricts one host.                                                                                                                                            | Worth knowing `priority`, `sizes`, and blur placeholder trade-offs, plus why unbounded `remotePatterns` is an SSRF/optimization-abuse risk (already partially mitigated here) — a concrete security nuance to be able to explain, not just configure.                                                                                                                                                                                                                                                                                                                  |
| B8  | **Metadata**                                                                        | Only static `metadata` export in root layout + `members/layout.tsx`. No `generateMetadata`, no per-page dynamic titles/OG.                                                                                                              | Dynamic `generateMetadata` can block streaming of the page shell if it awaits slow data without its own caching — a real performance nuance tying back to Track A's rendering model.                                                                                                                                                                                                                                                                                                                                                                                   |
| B9  | **`proxy.ts` (renamed middleware)**                                                 | Already implemented with a matcher and session check (documented in repo memory).                                                                                                                                                       | Edge-runtime constraints (no Node APIs), and that `revalidatePath`/`revalidateTag`/`cookies().set` cannot run inside it — worth being able to explain _why_ (it runs before the Node.js request-time cache/RSC render exists).                                                                                                                                                                                                                                                                                                                                         |
| B10 | **Route Handlers & Backend-for-Frontend**                                           | `src/app/api/{auth,pusher-auth,sign-image}` already use Route Handlers, but the _why_ (vs. a Server Action) hasn't been studied.                                                                                                        | Route Handlers are public, addressable HTTP endpoints reachable by any client (not just this app's UI) and can return any content type — the right tool whenever a caller lives outside the React tree (webhooks, third-party widgets like `pusher-js`/Cloudinary, a future non-Next client). Server Actions and Route Handlers share the same "not protected by the UI that calls it" security posture.                                                                                                                                                               |

## Risks / Trade-offs

- **Shallow practice risk** → Mitigation: each Track A/B task requires ideating several candidate exercises (mixing real-file adaptations and standalone playground features) before building one; Track C intentionally trades depth for breadth instead.
- **Docs drift from installed version** → Mitigation: all citations above were verified against the locally bundled docs for 16.2.10 and cross-checked live via `ctx7`/Context7 for `v16.2.9`; re-verify before each follow-up chat if `next` is upgraded.
- **Scope creep into product features** → Mitigation: this change and its follow-ups are explicitly learning exercises (see proposal); if an exercise turns into a real product improvement worth keeping, that's a bonus, not the goal.
